# 4. Store plot boundaries as `geometry(Polygon, 4326)`

- **Status:** Accepted
- **Date:** 2026-10-03

## Context

Each plot is the exact polygon a seller draws on the map. The backend has to reject polygons that overlap an existing plot. It also has to find plots within a radius in metres and filter by area. Coordinates travel as GeoJSON, which uses WGS 84 longitude/latitude (SRID 4326).

PostGIS offers two column types:

- `geometry` does planar math in the units of its coordinate system (degrees for 4326) and supports every spatial function.
- `geography` does math on the sphere, in metres, but supports only a subset of the functions.

## Decision

- The boundary column is `geometry(Polygon, 4326)`. The type modifier makes the database reject anything that is not a polygon in SRID 4326, such as a point or a polygon in web-map coordinates (3857).
- **Topology checks run on `geometry`.** The overlap rule needs `ST_Relate` / `ST_Touches`, which only exist for `geometry`, as do `ST_IsValid` and other topology functions.
- **Measurements cast to `geography`.** Distances and areas (radius search, area filters) use `boundary::geography`, so they come out in metres on the Earth's surface. Index support for those queries is added with the issue that introduces them.
- A GiST index on `boundary` serves overlap checks and viewport queries. It compares bounding boxes first, so the exact geometry tests only run on a few candidates.
- Database constraints back up the application's validation: `CHECK (ST_IsValid(boundary))` and `CHECK (price > 0)`. Invalid geometries are rejected, never repaired.
- IDs are UUIDs generated by the application, never sequential integers exposed in URLs. Other modules can reference a plot by ID without coordinating with the database.
- `price` is `NUMERIC(14, 2)`: exact decimal money, never floating point.

## Alternatives considered

- **`geography` column:** distances in metres for free, but no `ST_Relate`/`ST_Touches`, so the interior-overlap rule could not be expressed.
- **`geometry` in a projected, metre-based SRID (e.g. a UTM zone):** planar metres are accurate only near that zone. Plots can be anywhere, and every request would need reprojection to and from GeoJSON's 4326.
- **No database constraints, validation in Java only:** simpler, but any other writer (a migration, a script, a future endpoint) could store an invalid shape.

## Consequences

- Queries that measure must remember the `::geography` cast. A plain `ST_Distance` on this column returns degrees.
- The application validates geometry first, to return a clear 422. The constraints are a safety net, and a violation reaching them is a bug to be mapped as an error, not normal flow.
